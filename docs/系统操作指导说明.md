# lit-screener 系统操作指导说明

> 面向第一次使用本系统的人：不需要懂编程，跟着本说明一步步操作，就能完成一次完整的文献筛选。
> 全文分为六个部分：系统是什么 → 基本术语 → 使用前的准备 → 完整操作流程 → 看懂输出结果 → 常见问题排查。
> 最后附有**术语速查表**，遇到不认识的词随时翻到最后查。

---

## 一、这个系统是干什么的？

做科研综述时，从数据库里检索到的文献往往有几百上千条，需要人工逐篇阅读标题和摘要，判断"这篇是否符合我的研究主题"。这个系统就是**把这道人工初筛交给 AI 完成**：

```
你的文献数据（Excel/数据库导出）
        ↓
AI 双评审逐条对照你的筛选标准打分
        ↓
两 AI 意见一致 → 直接采纳；有分歧 → 第三个 AI 仲裁
        ↓
输出筛选结果 + 每篇的详细理由
        ↓
你只需人工复核少数"AI 拿不准"的文献
```

系统的可信度建立在三点上：
1. **不是笼统地问 AI"这篇相关吗"**，而是把标准拆成若干条明确判据，让 AI 逐条回答"是/否"并给出理由——错了能定位到具体是哪条标准判错；
2. **两个不同模型独立评审**，分歧本身就是"AI 拿不准"的信号，这些文献会被自动列进人工复核清单；
3. **全程留痕**，每一个判定都能查到当时 AI 的原始回答和推理，可审计。

## 二、基本术语（先混个脸熟，后文都会用到）

| 术语 | 通俗解释 |
|---|---|
| **题录 / 记录（Record）** | 一条文献的基本信息：标题、摘要、作者、年份、DOI 等。系统处理的基本单位。 |
| **判据（Criterion）** | 一条明确的筛选标准，例如"研究是否以脱氮为目标？"。AI 对每条文献要逐条回答每条判据。 |
| **判据包（criteria.yaml）** | 所有判据汇成的文件，还包含"领域身份"描述（告诉 AI 它是哪个领域的专家）。 |
| **主题包（themes/<主题名>/）** | 一个研究主题的全部配置打包在一个文件夹里（判据 + 知识库 + 运行配置）。换研究方向 = 换一个文件夹，不用改代码。 |
| **双评审（R1 / R2）** | 两个不同的 AI 模型，各自独立评审同一篇文献（互相看不到对方的答案）。 |
| **仲裁（Arbiter）** | 第三个（通常更强的）AI 模型。只在两个评审意见不一致时出场，对比双方理由后裁定。三者合称 RRA 流程。 |
| **纳入 / 排除（include / exclude）** | 一篇文献的最终判定：include = 符合所有判据，收进来；exclude = 至少一条判据不满足，排除掉。 |
| **金标准（golden labels）** | 你人工标注过答案的文献清单，用来"考试"——检验 AI 判得准不准。 |
| **few-shot** | 把你标注过的文献作为"参考例题"附在 AI 的题目里，让它模仿你的判断标准。 |
| **RAG / 知识库** | 把领域知识写成 Markdown 笔记，系统自动检索相关条目塞给 AI 作参考（可选功能）。 |
| **run_id** | 每次运行的时间戳编号（如 `20261024_164313`），输出文件全靠它区分是哪一次跑的。 |

## 三、使用前的准备（只需做一次）

### 3.1 环境要求

- macOS / Linux / Windows（命令示例以 macOS 终端为准）
- Python 3.10+
- 一个大模型 API 账号的密钥（本项目默认使用火山方舟，任何 OpenAI 兼容接口均可）

### 3.2 安装步骤

打开终端，逐行执行（`$` 是提示符，不要输入）：

```bash
$ cd /Users/zc/AIWorkspace/lit-screener     # 进入项目目录

$ python3 -m venv .venv                     # 第一次：创建独立 Python 环境
$ source .venv/bin/activate                 # 激活环境（每次开新终端都要先执行这句）

$ pip install -r requirements.txt           # 安装依赖（第一次）
```

### 3.3 配置 API 密钥

密钥放在项目根目录的 `.env` 文件里（该文件不会提交到 git）。如果还没有，参照模板创建：

```bash
$ cp .env.example .env
```

然后用文本编辑器打开 `.env`，填入你的密钥：

```
ARK_API_KEY=你的火山方舟密钥
```

> ⚠️ **重要**：命令行不会自动读取 `.env` 文件。每次运行前需要先执行（或把这段加进你的 `~/.zshrc`）：
> ```bash
> $ set -a && source .env && set +a
> ```
> 忘了这步会报错"环境变量 ARK_API_KEY 未设置"——这是最常见的第一个坑。

### 3.4 确认系统是通的（不花一分钱）

```bash
$ python -m litreview.cli screen --config config.yaml --mock --limit 5
```

`--mock` 表示用假 AI 走一遍流程，不调用真实模型、不花钱。看到输出文件列表即说明系统正常。

## 四、完整操作流程（以实际案例：998 条厌氧氨氧化文献为例）

下面以"筛选出同时符合**厌氧氨氧化、脱氮、废水处理**的研究性论文、英语、2000.01.01–2026.09.30"这个真实需求为例，走一遍全流程。**换成你的主题时，只是判据和数据不同，步骤完全一样。**

### 第 1 步：准备数据文件

系统支持三种输入格式（自动识别）：

| 格式 | 说明 |
|---|---|
| **CSV** | 表格文件，列名含 `Article Title`（标题）和 `Abstract`（摘要）即可 |
| **RIS** | Web of Science / Scopus / EndNote 的通用导出格式（`.ris`） |
| **WoS 制表符** | Web of Science "导出为制表符分隔文件"（`.txt`） |

**你的数据是 Excel（.xlsx）怎么办？** 系统不直接读 xlsx，需要先转成 CSV。让 AI 助手帮你转，或者用 Excel 的"另存为 → CSV UTF-8"。转换后放到项目的 `data/` 目录下，例如 `data/998.csv`。

> 💡 **列越全越好**：如果你的表里还有 `DOI`、`Language`（语种）、`Document Type`（文献类型）、`Publication Date`（日期）列，系统会自动识别并用于预过滤，省钱又提速。只有标题+摘要+年份也能跑——缺的字段由 AI 判据兜底判断，只是多花一些模型调用。

**数据要求**：标题列必须有；强烈建议每条都有摘要（配置了 `require_abstract: true` 时缺摘要的会被直接剔除）。

### 第 2 步：检查主题包（以 anammox 为例）

```bash
$ ls themes/anammox/
config.yaml   criteria.yaml   knowledge.md   labels_template.csv
```

- **`criteria.yaml`** —— 判据包。打开看一眼，五条判据正好覆盖本需求：
  - **A1** 厌氧氨氧化核心（研究对象含 anammox 或其耦合工艺）
  - **A2** 脱氮目标（氮去除是核心指标）
  - **A3** 废水处理场景
  - **A4** 研究类型（排除综述/评论，只要研究性论文）
  - **A5** 语种（英语）
- **`config.yaml`** —— 运行配置。里面已设好日期过滤 `2000-01-01 ~ 2026-09-30`、三个 AI 模型等。
- 如果是**新研究方向**：运行 `python -m litreview.cli new-theme themes/我的主题` 生成模板，然后重点改写判据的 guidance（见第 7 步调优）。

### 第 3 步：为你的数据建运行配置

复制一份主题配置，把数据源指向你的文件。本案例已建好 `themes/anammox/config_998.yaml`，关键字段是：

```yaml
data:
  inputs:
    - type: file
      path: data/998.csv        # ← 指向你的数据文件

filters:                        # 硬性条件，代码直接过滤，不花 AI 调用
  language: en
  date_from: "2000-01-01"
  date_to: "2026-09-30"

criteria:
  active: [A1, A2, A3, A4, A5]  # 启用哪几条判据
  inclusion_logic: all          # all = 全部满足才纳入
```

> ⚠️ **必须进入项目根目录再运行**，配置里的相对路径都以项目根目录为基准。

### 第 4 步：预览过滤效果（不花 AI 调用，免费）

```bash
$ python -m litreview.cli screen --config themes/anammox/config_998.yaml --filter-only
```

会输出类似：

```
加载题录 998 篇（去重后）
过滤后剩余 998 篇
过滤预览已写出: output/filter_preview_xxx.csv
```

打开预览 CSV 检查：被剔除的是不是真的该剔（语种、年份不对的）。**确认数据被正确读入、该留的留下了，再进行下一步。**

### 第 5 步：小批量试跑（强烈建议，先跑 30 篇看效果）

```bash
$ set -a && source .env && set +a    # 别忘了加载密钥
$ python -m litreview.cli screen --config themes/anammox/config_998.yaml --limit 30
```

大约 2~5 分钟。跑完打开 `output/results_xxx.csv` 快速抽查：纳入的像不像你想要的？排除的冤不冤？

> 实测案例（2026-10-24）：30 篇中 29 纳入、1 篇被 A4 判据排除（是综述类），两评审一致 29 篇、仲裁 1 篇，全部判定成功无解析失败。

### 第 6 步：全量运行

确认试跑效果满意后，去掉 `--limit` 跑全量：

```bash
$ python -m litreview.cli screen --config themes/anammox/config_998.yaml
```

998 条约需 30~60 分钟（双评审 + 并发 10 线程）。**中途关掉终端也不会留下半成品文件**——系统是跑完一次性写输出的，重跑即可。

### 第 7 步：（可选，但强烈推荐）标注金标准 → 评估 → 调优

这是把筛选精度提上去的关键闭环：

```bash
# 1) 人工标注 50~100 篇：拿 labels/sample_golden.csv 当模板，
#    每篇填 DOI/标题 + 各判据 1(是)/0(否) + overall
# 2) 用 trace 文件（注意不是 results.csv）做评估：
$ python -m litreview.cli evaluate \
    --results output/trace_xxx.jsonl \
    --labels labels/你的金标准.csv
```

评估报告会给出**每条判据的精确率/召回率/F1**。哪个判据分最低，就回 `criteria.yaml` 把那条的 guidance 写得更明确，然后重跑。标注好的金标准还能在配置里开启 `fewshot:`，作为参考例题自动注入给 AI。

## 五、看懂输出结果

每次运行在 `output/` 目录生成四个文件（文件名里的时间戳就是 run_id）：

| 文件 | 内容 | 你要拿它做什么 |
|---|---|---|
| `results_*.csv` | 每篇的最终决定（include/exclude）+ 逐判据 是/否 + 判定路径 | **主结果**。筛选出来的数据集就是这里 decision=include 的行 |
| `disputed_*.csv` | 人工复核清单：AI 有分歧的、边界情况、解析失败的 | **你只需要看这个文件里的文献**，逐篇人工定夺 |
| `trace_*.jsonl` | 全程留痕：每个 AI 的逐判据回答和理由、仲裁记录 | 想查"某篇为什么被判排除"时翻它；也是 evaluate 的输入 |
| `stats_*.md` | 汇总统计 + 逐判据通过率 | 快速概览；看哪条判据淘汰最多，针对性优化 |

### results.csv 怎么读

```
id, doi, year, title, decision, human_review, review_reason, path, A1, A2, A3, A4, A5
```

- `decision`：include / exclude / undetermined（无法判定，进人工清单）
- `path`（判定路径）：
  - `consistent` = 两评审一致，直接采纳
  - `arbitrated` = 有分歧，经仲裁裁定
  - `single_reviewer` = 单评审模式
  - `parse_error_or_error` = 解析失败，**需人工**
- `A1~A5` 各列：该判据最终的 是(True)/否(False)

### 三种运行模式怎么选

在配置的 `run.mode` 里设置：

| 模式 | 什么时候用 | 行为区别 |
|---|---|---|
| `recall` | 系统性综述，**一篇都不能漏** | 排除一篇需两评审一致同意或仲裁确认；拿不准的一律进人工清单（人看得多，漏得少） |
| `precision` | 构建干净的数据集 | 只有评审真正分歧的才进人工清单（人看得少，可能混入少量错误） |
| 追踪模式 | 日常追新文献 | 把配置里 `reviewer_2` 改为 `null`（省一半调用），配合 `--since 2025-01-01` 只筛新文献 |

## 六、常见问题排查（FAQ）

**Q1：报错 `环境变量 ARK_API_KEY 未设置`**
忘了加载密钥。执行 `set -a && source .env && set +a` 后重试。

**Q2：报错 `文件 xxx 中找不到标题列`**
CSV 的标题列名不在识别范围内。把列名改成 `Article Title`（或 `Title` / `Document Title`）。

**Q3：报错 `ValueError: I/O operation on closed file` 之类的奇怪语法/运行错误**
先确认没改坏代码：跑一次 `python -m litreview.cli screen --config config.yaml --mock --limit 5`，mock 模式能定位问题是否在代码层。

**Q4：中文文献被排除了？**
本系统 anammox 主题包只收英语文献（A5 判据 + `filters.language: en`）。如需收中文，改判据包 A5 和过滤配置。

**Q5：跑全量太贵/太慢，能省点吗？**
- 先用 `--filter-only` 把明显不符的硬条件（语种/日期/类型）在元数据层剔掉；
- 只启用必要的判据（`criteria.active` 少一条就省一批调用）；
- 日常追踪用单评审模式（`reviewer_2: null`）。

**Q6：AI 判得不准怎么办？**
按第 7 步闭环来：标注金标准 → evaluate 看哪条判据最弱 → 改那条的 guidance（"纳入/排除/边界"三段写得越具体越准）→ 重跑。guidance 是精度的最大杠杆。

**Q7：结果的 include 里混进了明显不相关的？**
检查是哪条判据放行的（看 results.csv 的 A1~A5 列），去把该判据的"排除"段写得更明确。

**Q8：换了个新研究主题怎么办？**
`python -m litreview.cli new-theme themes/新主题` 生成模板 → 改判据和 config → 用 `--filter-only` 和 `--limit 30` 先试 → 再全量。全程不改一行代码。

## 附：术语速查表（按字母排序）

| 术语 | 英文/全称 | 一句话解释 |
|---|---|---|
| 仲裁 | Arbiter | 第三方 AI，评审有分歧时出面裁决 |
| 判据包 | Criteria Pack | 判据 + 领域身份描述的 YAML 文件 |
| CSV | Comma-Separated Values | 逗号分隔的纯文本表格，Excel 可另存为此格式 |
| DOI | Digital Object Identifier | 论文的全球唯一编号，如 `10.1000/abc.123`，用于精确去重 |
| F1 | — | 精确率和召回率的调和平均，越接近 1 越好 |
| few-shot | — | 给 AI 看几道"带标准答案的例题"再让它做题 |
| 金标准 | Golden labels | 人工标注的答案，用于给 AI "阅卷打分" |
| 题录 | Record | 一条文献的标题、摘要、作者等信息集合 |
| RAG | Retrieval-Augmented Generation | 检索增强生成：先从知识库里翻出相关笔记再喂给 AI |
| recall 模式 | — | 宁可错杀不可放过，系统综述用 |
| precision 模式 | — | 追求结果干净，构建数据集用 |
| RIS | Research Information Systems | 文献管理软件通用导出格式 |
| RRA | Reviewer-Reviewer-Arbiter | 双评审 + 仲裁的流程代号 |
| temperature | — | AI 的"随机度"，本项目固定为 0（每次回答尽量确定一致） |
| trace | — | 全程留痕文件，记录 AI 的每一步原始回答 |
| TF-IDF | — | 一种简单的文本检索算法，用于知识库条目匹配（离线、无需显卡） |
| WoS | Web of Science | 常用文献数据库，其导出格式被本系统直接支持 |
